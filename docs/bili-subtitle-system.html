② 字幕轨目录：两个平行接口

这是设计的核心——同一个字幕目录有两个入口，格式不同：

接口格式鉴权现状
/x/player/wbi/v2 JSON data.subtitle.subtitles[] 需 Wbi 签名 仍可用，同时含 CC + AI 轨（Bilibili-Evolved #4795 确认）T2
/x/v2/subtitle/web/view protobuf（octet-stream） 需登录（不登录返回空） 新版播放器主用；迁移 protobuf 后未登录拿不到字幕目录（beefreely #5）T2

关键：早期认知「player/wbi/v2 只含 CC、AI 走 subtitle/web/view」不准确。两个接口都含 CC+AI 全量轨道，只是格式（JSON vs protobuf）和鉴权不同。新版播放器优先用 protobuf 接口。

subtitle/web/view 的 protobuf 结构（BiliOne/BiliSubtitleApi.kt 逆向）T2：

请求: oid=&pid=&context_ext={"video_type":1}&type=1&cur_production_type=0
     Accept: application/octet-stream
响应: protobuf 二进制
  field 1 = VideoSubtitle (顶层)
  field 3 = repeated track 列表
    每个 track: f1=id, f2=id_str, f3=language(ai-zh), f4=label,
                f5=source_url, f7=type, f9=ai_type, f10=ai_status

两个目录接口「谁是主、谁喂谁」的数据流关系未被权威证实（SourceRelay 标 inconclusive）。扩展实践（KenEasy-BiliCC-Exporter）是同时 hook 三个接口从任一个提取字幕列表。T2/T3

关键认知：空字幕 ≠ 无字幕
subtitle.subtitles 文档备注明确「不登录为 []」。对充电专属视频，服务端访问控制让未付费/未登录用户拿到空字幕列表 + preview_toast（「为创作付费，购买观看完整视频」）。
所以「字幕轨为空」是权限不够，不是「该视频没字幕」。已充电用户访问能拿到完整轨道。
「充电」≠ 大会员/BVIP：充电是创作者打赏/包月支持体系，单独的付费层。

四、AI 字幕的「加密墙」（核心技术难点）

这是第三方采集 AI 字幕的最大障碍，也是最容易误解的地方。两种情况并存：

情况 A：现代明文 aisubtitle.hdslb.com

URL 明文，正文明文 JSON，带 auth_key 鉴权参数。第三方能直接 GET（SourceRelay 实测 200 JSON）。 障碍不在 URL 本身，而在「拿不到 URL」——目录已迁 protobuf（不便 JSON 解析）+ 需登录。T3

情况 B：旧域名 subtitle.bilibili.com 的 XOR 加密 path（含 %00）

实测充电视频的 subtitle/web/view protobuf 里正则抠出的 URL 全是这种加密形态（T3 实测）：

https://subtitle.bilibili.com/%01%1B%5C=_%04%12%12%049f%2F%07...?auth_key=1786636221-...

（path 是 XOR 密文，percent-encode 后含 %00-%1f 控制字符）

XOR 解密算法（两个独立逆向库完全一致复现，强佐证）T2：

// 来自 vruses/beefreely useCrypt.ts + BiliOne BiliSubtitleApi.kt
fullKey = keySeed + 'bilibili'               // 硬编码密钥串
plain   = xorDecrypt(decodeURIComponent(encryptedPath), fullKey)
// 解密后得到干净的 path: /bfs/ai_subtitle/prod/
// 拼成明文: https://aisubtitle.hdslb.com?auth_key=...

来源：beefreely/useCrypt.ts · BiliOne/BiliSubtitleApi.kt

为什么第三方 fetch 加密 URL 失败？
加密 path 含 percent-encoded 控制字节（%00→null 等），按 WHATWG URL 规范 URL 不能含未编码 C0 控制字符/null， 浏览器在 fetch 层直接拒绝（实测 Chrome 报 "Failed to fetch"）。
播放器能拿到：因为它在 bpx-player JS 内部先 XOR 解密出干净的 aisubtitle.hdslb.com URL 再 fetch——纯客户端、无签名接口、key 是硬编码字符串。
采集策略：第三方不自己重建解密，而是拦截播放器已解密的明文请求（hook fetch/XHR）——本项目 subtitle-collector 即用此法。

① AI 视频总结接口 · 隐藏的第三字幕来源

这是本次调研最有价值的新发现。即使原视频 player 接口没字幕，AI 视频总结接口可能提供带时间轴的 AI 字幕，可作兜底字幕源：

GET https://api.bilibili.com/x/web-interface/view/conclusion/get
    参数: aid/bvid, cid, up_mid, cloc（WBI 签名）
响应: data.model_result.subtitle[] → 每条含 part_subtitle[]
       part_subtitle: { content, start_timestamp, end_timestamp }  // 带时间轴的 AI 字幕
       另有 outline（大纲）/ summary（纯文本总结）
⚠ 验收实测（游客态）：此接口返回 code=-101「账号未登录」，必须有登录态 cookie 才能拿到。 T3 实测 · 作为兜底字幕源可行，但前提是采集端已登录。

video/summary.md T1 · 注意：固定翻成中文，时间轴精度可能不如正字幕。

② 国际版 bstar · 完全独立的字幕系统

bilibili.tv（国际版）有自己的一套字幕 API，和国内完全不互通，主打多语言翻译字幕：

③ 字幕投稿接口族 · 反向只读端点

UP 主投稿字幕的接口族 /x/v2/dm/subtitle/*，其中有一个只读端点可查「某 cid 支持哪些字幕语言」（虽拿不到内容，但能预判有无字幕+补全语言码）：

GET /x/v2/dm/subtitle/lan/search/cid?type=1&oid=  → data.lans[]（语言列表，无内容/URL）
POST /x/v2/dm/subtitle/draft/save                        → 投稿写入（需 UP 主 csrf，不可反读）
POST /x/v2/dm/subtitle/del                               → 删除字幕

八、采集启示（第三方如何拿字幕）

基于以上 B 站设计，第三方采集字幕有几条路径，权衡如下：

路径可行性限制
A. 服务端主动调 API（view → player/wbi/v2 → fetch CDN） CC 字幕可行；普通视频 AI 字幕可行（player/wbi/v2 含 AI 轨） 需登录态 cookie；充电视频 need_login_subtitle + 付费墙 → 空轨；旧加密 URL fetch 被拒
B. 客户端拦截播放器请求（hook fetch/XHR） 最通用：CC + AI（明文/加密解密后）都能拿到 必须打开页面让播放器跑；依赖 inject 注入未被覆盖
C. 自己 XOR 解密 理论可行（算法公开） 脆弱：B 站改 key/算法即失效；需逆向跟进。不推荐

本项目 subtitle-collector 采用 A + B 混合：普通视频走 A（background 主动抓）；只有 AI 字幕的充电视频走 B（被动拦截 + 自动点字幕按钮触发播放器解码）。详见 bili-fetch.js（A 路径 + 加密 URL 过滤）和 inject.js（B 路径拦截）。
