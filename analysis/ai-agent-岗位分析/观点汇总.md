## 1. 岗位定义与边界

**FDE（Forward Deployed Engineer，前沿部署工程师）是原料中定义最集中的岗位**：

- 一句话定义：把大模型、RAG、Agent 这些前沿技术真正接近企业业务，并且**对落地结果负责**；"会调 API、会搭 agent demo 只是入门"。
  > 来源: FDE薪资 [00:12]
- 直白版定义：在 AI 工具加持下，到客户现场，把客户（常常一句话的模糊）需求变成一个跑得通的、生产环境可用的系统。这个岗位**不是研究模型的**，是让模型在客户生产系统上落地。
  > 来源: FDE实战直播 [05:12]
- 岗位画像："FDE 本质上更像 AI 工程师 + 产品经理 + 技术顾问 + 项目交付"，且"目前更偏中高级岗位"。
  > 来源: FDE薪资 [01:12]
- 岗位的两种存在形式：一种去客户现场（出差驻场），另一种是"内部 FDE"（也有公司叫 AI BP），即在自己公司把 AI 落到自己的业务里。
  > 来源: FDE实战直播 [07:25]
- **FDE ≠ 售前、≠ 运维、≠ 驻场外包**三个边界：售前讲完方案签单就走，FDE 是"签完才开始"并对结果负责（腾讯 JD 原话"主导落地交付上线护航"）；运维保证系统不挂，FDE 决定系统"该变成什么样子"（字节 JD 原话"独立完成技术架构决策"）；外包按人天卖时间听甲方指挥，FDE "对客户业务结果指标负责"。UP 也承认行业里有人管这岗叫"高级驻场外包"，区分标准是"按人天赚钱还是对结果负责"。
  > 来源: FDE实战直播 [08:16]、[08:44]、[09:13]
- **FDE 在国内招聘网站有一堆"马甲"**：四家大厂对同类岗位叫法完全不同——腾讯叫"AI前线部署工程师"、字节叫 forward deployed engineer、阿里云叫"前沿部署工程师"、蚂蚁叫"客户技术解决方案架构师（FDE 方向）"，还有公司归在"交付中心"。"只搜 FDE 会错过很多岗位，识别马甲本身就是求职能力"。【分析者推断：此段为 UP 个人抓取的 2026-07 数据转述，JD 原文无法从原料内核对】
  > 来源: FDE实战直播 [28:55]
- FDE 高薪的商业逻辑："一个人就是代表一个团队"——一个人把以前四五个人才能搞定的事搞定，"你一个人干四五个人的活，老板给你发三人工资，老板省钱你也赚钱"。【该说法为 UP 个人经验之谈】
  > 来源: FDE实战直播 [1:01:22]

**国内机构视角下的岗位谱系**：

- 培训机构视角："AI 大模型岗位"原本分三个——大模型应用开发工程师、大模型研发工程师（又称应用算法工程师）、大模型算法工程师；但到 2025 年底"纯大模型岗位只剩两个了"，纯只会应用开发（Agent/RAG/私有化部署）的岗位"几乎没有了"。
  > 来源: 码士集团 [05:31]、[08:13]
- 求职科普视角：AI 方向分两条路线——应用落地路线（AI 应用工程师、Agent 智能体工程师、AI 产品/AI 解决方案）与技术深度路线（机器学习工程师、大模型算法工程师、AI 基础设施工程师）。
  > 来源: 2026岗位盘点 [00:15]
- 低代码/无代码一端的"智能体搭建"岗：用扣子（Coze）这类工具搭工作流即算上岗，上海有岗位"大专、学历不限"，岗位名有"智能体搭建师、扣子智能体"等。【分析者推断：该视频展示的招聘信息为口述，未给出平台与职位原文截图，岗位普遍性无法验证】
  > 来源: 智能体案例薪资 [00:15]
- 海外语境佐证 FDE 的分量：转述硅谷评论——"面向企业最好的商业模式，不是卖大路货的 API 访问权，而是把他们自己的模型卖给他们"，thinking machines 类公司靠"成为企业定制模型领域的 FDE"、向最大型企业收 7~9 位数费用做防火墙内后训练。【注意：这是播客对推文的转述，属行业评论而非岗位描述】
  > 来源: 三位工程师播客 [21:36]

**四大核心能力框架**（对"大模型应用开发工程师"的职责归纳）：任务拆解（判断该用一句 prompt、工作流还是多 agent 协同）、工具调用（权限/异常/上限/编排）、评测与可观测性（追踪/回放/调试）、生产交付（状态管理/断点恢复/日志监控/风险防护/成本优化）；"前两点决定能不能做出来，后两点决定做出来的是玩具还是产品"。
> 来源: 四大能力 [00:35]、[01:22]

## 2. 日常工作内容

**FDE 的交付全流程（六步/七步）**——来自一场 40 分钟无剪辑直播实操（从一句话需求做到手机可访问的公网系统）：

1. 澄清需求：把"客户说我想要一个 AI"变成方案——给谁用、解决什么问题、不做什么、三条可验证的验收标准；拿不准的不许问、必须写成"假设清单"留给客户逐条确认。
   > 来源: FDE实战直播 [10:16]、[21:00]、[23:36]
2. 定数据契约：两边数据结构和口径对齐，字段怎么对、拿不准谁拍板；产出 PRD 与 JSON 字段设计。UP 称这一步"最像 FDE 的内容"。
   > 来源: FDE实战直播 [10:42]、[25:42]
3. 处理脏数据：格式不统一、口径打架、缺字段——"真实的数据从来都是有各种问题的"；且数据来源要可审计（"客户一定会问数据怎么来的"）。
   > 来源: FDE实战直播 [10:57]、[30:48]
4. 把东西做出来：UP 的观察是"以前这步最麻烦，现在反而是最快的一步，因为 AI 完全可以自己开发项目"。
   > 来源: FDE实战直播 [11:06]
5. 人工检验/自测挑毛病："AI 可能会说测好了没问题，实际有没有问题需要人工再去检验"，且要求 AI"不许编，用真实接口数据列出问题"。
   > 来源: FDE实战直播 [11:35]、[37:52]
6. 上线交付与验收：部署到生产、客户验收；直播中现场翻车（AI 写的页面数据没出来、自检环节卡死 20 分钟最后手动打断）——UP 自己承认"现场实操很不可控"。
   > 来源: FDE实战直播 [11:56]、[34:13]、[43:34]

**每一步都对应大厂 JD 的原话**（UP 的核心论证）：阿里 JD"明确目标边界与验收标准"＝需求澄清；腾讯 JD"MCP 打通 CRM/ERP/OA"＝字段对齐；字节 JD"构建评估管道和可观测框架"＝自测挑毛病；腾讯 JD"客户高管沟通与现场问题拆解能力"＝需求沟通。【分析者推断：JD 原话为 UP 转述，无法独立核验，但与原料中其他视频对能力的要求相互印证】
> 来源: FDE实战直播 [47:52]

**企业落地卡点在"最后一公里"而非模型能力**，具体是四件事：用户说不清真正需求；生产数据是脏的；原有系统难连接；交付上线没人敢对结果负责——"没有一件事是 AI 能自己解决的"。
> 来源: FDE实战直播 [05:56]

**海外一线 ML 工程师的 Agent 自动化日常**（Hugging Face 社区科学团队，自动化"邀请研究者把模型迁到 HF"的 outreach 工作）：

- 人工流程：看到 arXiv 新论文 → 找 GitHub 链接 → 读 README → 判断有没有值得发布到 HF 的权重/数据集 → 提 GitHub issue 或提交 PR → 跟进作者。arXiv 每天数百篇论文，"对我来说并不可扩展"，所以要自动化。
  > 来源: HF工程师实战 [04:24]
- 技术选型的思考框架：确定性 workflow（预定义路径中调 LLM API，可预测、可控、灵活性低）vs 完全自主 agent（循环调用工具直到完成，灵活但不可预测），"不必非黑即白，可以混合搭配"。
  > 来源: HF工程师实战 [05:08]
- 2024 年第一版**刻意不用任何 agent 框架**，纯 LLM API + 确定性 workflow——因为当时 Anthropic《构建高效代理》的建议就是"尽量避免构建 agent，从单个 LLM API 起步，避免使用框架"；部署只是 GitHub Actions 上的每晚 cron 任务。
  > 来源: HF工程师实战 [06:02]、[06:45]、[07:02]
- 2025 年跟进环节改为**完全自主 agent**（Claude Agents SDK），理由是"模型能力大幅提升，现在可以尝试完全自主代理而非工作流"；并引用 Cursor 的演讲：用 200 行代码的"技能"替代 12000 行复杂工作流。
  > 来源: HF工程师实战 [09:10]、[09:58]
- 日常运维内容：LangSmith 追踪每次处理的输入输出、成本、延迟；批量处理时"同时启动大量容器并行运行，每个容器相当于一个智能体循环处理单个 GitHub issue"。
  > 来源: HF工程师实战 [07:54]、[12:04]
- 对" agent 会不会骚扰人"的实际反馈：数千个 issue 中只收到两条负面评论，多数作者感谢；甚至常看到"人们用 agent 回复我的 agent"——"这就是现在的互联网"。
  > 来源: HF工程师实战 [14:10]、[14:21]

**国内教学视角的日常技术细节**（Agent 开发具体在写什么）：

- 记忆系统设计：内存型记忆、全局记忆、持久化记忆三级；持久化走向量存储（pgvector、Milvus 等）；工作流引擎里做全局变量池与节点作用域变量、占位符替换。UP 强调"这些专业术语一定要参与过企业级项目才真正说得出来"。
  > 来源: 工作流编辑器记忆 [00:16]、[01:16]、[00:42]
- human-in-the-loop：很多 AI 流程需要人工介入——用 LangGraph 的 interrupt 挂起等待人工审批（approve/reason/question/instruction 四要素），人工输入后用 command resume 恢复执行；状态靠 checkpoint 持久化。
  > 来源: human in the loop [00:03]、[01:01]
- 结构化输出与状态图：定义 sentiment/diagnosis 等 schema 让模型输出 structured output，用 conditional edge 做情感分流（positive 直接回复、negative 先诊断再生成）；UP 边讲边吐槽这套 API"增加了复杂度"，并质疑"直接搞一些 tool call 应该也能跑这种东西"。
  > 来源: 内容审核工作流 [01:41]、[09:56]

**agentic coding 工程师的一线工作流**（Cloudflare 工程师 Dylan 的自述，代表了"用 AI 写代码的工程师"现在的样子）：

- 工具链：极简 agent harness（4 个工具：读、写、bash，system prompt 不到 1K token）+ 终端多路复用器（为 agent 时代的 tmux）+ 本地代码批注/审查工具；十几年终端老手，"现在很少再钻进代码编辑器"。
  > 来源: 三位工程师播客 [37:40]、[44:10]、[47:09]
- 工作方法：动手前先向 agent 抛一连串自己已知或想知道答案的问题来收集 context；spec 不写成 PRD 而写成"伪代码"，做"类型驱动开发"——让 agent 先列类型、函数边界、每层输入输出类型/副作用/可能的错误，"逼着他一条条列出来"以对齐抽象预期。
  > 来源: 三位工程师播客 [49:40]、[54:52]、[55:18]
- 对 sub-agent 的保留态度："自主运行的 sub-agent 有一种倾向，太容易把思考这件事从开发者手里拿走"，所以 prompt 编写和 context 收集坚持亲手做。
  > 来源: 三位工程师播客 [51:26]
- AI 代码的通病观察："我从没见过哪个模型会说'这个文件太大了，我得重构一下'——他们感受不到那种摩擦力"；还爱"一口气造出一大堆特别细碎的小抽象、用完一次就扔的适配器"，所以要故意在引入新抽象上加阻力。
  > 来源: 三位工程师播客 [59:43]、[59:55]
- 产出与代价："能同时推进两三个 feature，比以前累多了，但产出确实更高了"；同一播客里另一位自述一周写 5-6 万行代码后直接 burnout 请假两周。行业级的"焦头烂额"被三位当事人都点到。
  > 来源: 三位工程师播客 [1:07:44]、[1:10:55]、[1:11:45]
- 转型时间线：Opus 4.5 出来之前对 AI 不感冒，用了之后"很快意识到 agentic engineering 就是未来"；且"这是一套完全全新的技能，你得从头一点点学起……从过去那套工作流一步跳过来拿不到漂亮结果"。【分析者推断：说明连资深工程师的转型也是近一两年的事，岗位方法论尚在快速演化】
  > 来源: 三位工程师播客 [35:39]、[36:34]

## 3. 技能栈与招聘要求

**FDE 四类能力清单**（营销号版本，但与 S4 的 JD 引用互相印证）：

1. AI 应用开发：Python、大模型 API、RAG、Agent、各类框架、MCP——"但更重要的是知道什么时候用 RAG、什么时候上 Agent、什么时候一个 workflow 就可以了"。
2. 软件工程：API、数据库、Docker、云部署、系统集成、日志监控——"企业要的不是能跑一次，而是能上线、能稳定、跑出了问题还能查"。
3. 企业级 AI 工程：模型答错怎么办、tool 调用失败怎么办、权限/成本/延迟怎么控、评测监控和人工兜底——"这些才是 demo 和真实项目最大的差距"。
4. 业务和交付：听懂客户要解决什么问题、判断场景该不该用 AI、能否真正提效降本。
   > 来源: FDE薪资 [00:24]

**大厂 Agent 岗面试的两条考察主线**（培训机构面试辅导视角）：

- 理论深度：项目有没有动过底层模型——对 embedding 模型做过特定优化吗？意图识别模型？后训练/强化学习微调改造？向量数据库怎么提升召回、怎么加 re-rank 模型、re-rank 模型二次微调？"如果只是调 API 纯跑工程，那就是一个后端开发工程师的角色，测不出理论。"
  > 来源: 大厂面试两点 [00:19]
- 工程深度：连环追问——高并发怎么解决、异步怎么处理、agent 长短期记忆设计了几层机制、缓存为什么这么设计、TTFT 经历了几轮优化、用户量提升 10 倍/100 倍怎么办、所调用的模型宕机了兜底方案是什么、服务堵塞的降级策略是什么。
  > 来源: 大厂面试两点 [00:59]

## 6. 共识 与 分歧

### 共识（多方一致）

1. **调 API、搭 demo 只是入门；生产化能力才是稀缺项**——评测、监控、人工兜底、容错、成本控制被点名的频率最高。
   > 来源: FDE薪资 [00:20]、四大能力 [01:22]、大厂面试两点 [00:59]、码士集团 [08:26]、HF工程师实战 [18:34]
2. **企业落地的瓶颈不在模型能力，在"最后一公里"**——需求澄清、脏数据、系统集成、责任承担；对应地，"智能 vs 专长"的学理版本：模型智能已很强，缺的是对每个企业"微观世界"的专长与在岗持续学习。
   > 来源: FDE实战直播 [05:56]、智能≠专业 [04:51]、[05:31]
3. **workflow 还是 agent 按场景选，没有万能架构**——确定性要求高用 workflow，灵活性要求高用 agent，可混合；选型看业务复杂度与可控性要求。
   > 来源: HF工程师实战 [05:08]、面经合集 [00:46]、内容审核工作流 [09:56]、FDE薪资 [00:33]
4. **工程背景 + 行业经验的人转岗优势最大；纯新人不占优**。
   > 来源: FDE薪资 [01:20]、FDE实战直播 [12:57]、[56:21]、2026岗位盘点 [02:13]
5. **Python 是底座，LangGraph 是国内教学主流编排框架，MCP 是 2026 年新增热点**（秋招 JD 里多处点名）。
   > 来源: 分群体路线 [01:05]、26秋招盘点 [00:27]、大厂面试两点 [00:37]
6. **"对结果负责"是这个岗位区别于传统开发/售前/外包的标识**。
   > 来源: FDE薪资 [00:18]、FDE实战直播 [09:26]

### 分歧（说法相左）

1. **市场冷热**：
   - 立场甲（营销号集体）：高薪缺人——"70K""百万年包""729% 增长""几十万预算招不到人"。
     > 来源: 26秋招盘点 [00:03]、FDE薪资 [01:29]、四大能力 [00:02]
   - 立场乙（培训机构内部视角）：2025 年底面试明显变难、薪资被压、跌破 2 万的 offer 出现、纯应用岗几乎消失。
     > 来源: 码士集团 [02:56]、[03:48]、[08:35]
   - 【分析者推断】两者不必然矛盾：营销号描述的是头部稀缺岗，码士描述的是培训班学员 bulk 就市场；但至少说明"学了就高薪"的叙事不成立。
2. **只学应用开发（Agent/RAG）够不够**：
   - 立场甲：不够——面试已掺 20%~30% 微调/算法问题，"只学应用的课程承诺 2 万以上岗位是骗人的"。
     > 来源: 码士集团 [05:09]、[08:52]
   - 立场乙（隐含）：够——多数营销号课程仍以 Agent/RAG/MCP 应用开发为完整卖点。
     > 来源: 2026岗位盘点 [00:20]、四大能力 [00:30]
3. **低代码 vs 代码派**：
   - 立场甲：扣子等低代码智能体搭建即可就业、学历不限。
     > 来源: 智能体案例薪资 [00:15]
   - 立场乙：只会 LangChain 编排"天花板很低、要不出溢价"，秋招岗要求 harness/coding agent 深研。
     > 来源: 分群体路线 [01:21]、26秋招盘点 [00:57]
4. **要不要学微调/后训练**：
   - 立场甲（面试视角）：大厂爱问 embedding 优化、后训练、RL 微调、re-rank 二次训练，是加分主线。
     > 来源: 大厂面试两点 [00:19]
   - 立场乙（一线工程视角）：企业场景用 skill + 可随时替换的底座模型更划算，"我更愿意把它固化成 skill 和指令，这样能按需随时把底层模型换掉，而不是搞一个微调好的模型"；同时另一派押注企业定制后训练是最高价值环节。
     > 来源: 三位工程师播客 [26:35]、[21:36]
5. **agent 自主程度**：
   - 立场甲：模型能力提升后应转向完全自主 agent（200 行技能替代 12000 行工作流）。
     > 来源: HF工程师实战 [09:10]、[09:58]
   - 立场乙：警惕 sub-agent 把思考从开发者手里拿走，spec/类型/架构决策必须人握在手里。
     > 来源: 三位工程师播客 [51:26]、[59:01]
   - 【分析者推断】分歧根源是任务性质不同（批量重复 outreach vs 抽象设计敏感的核心代码），未必是路线冲突。
